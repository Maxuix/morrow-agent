# Stage 4 Domain and Durable Conversation decision

## Status

Accepted for Stage 4 implementation planning by S4.35.3. No production persistence is implemented
by this decision.

This decision closes the domain, idempotency, ConversationLog, sequence, and `/new` blockers found
in [`docs/reviews/stage-4-plan-review.md`](../reviews/stage-4-plan-review.md).

## Current-code facts

The Stage 3 runtime is process-local, not partially durable:

- bootstrap creates a fresh `Session` before the first user input;
- `AgentRuntime.run_turn()` delegates to the same `AgentLoop.run_task()` and production composition
  may supply a `ToolExecutor`;
- `ConversationLog._next_sequence()` allocates in-memory positions and append methods mutate
  `_records` immediately;
- `turn.started` is emitted before `ConversationLog.begin_turn()`;
- `turn_id` is reused as the process-local `ToolRunContext.run_id`;
- `/new` resets the same Session object and `/exit` treats conversation history as unsaved memory;
- no TaskRun, AgentRun, durable receipt, or durable conversation record exists yet.

Subplan 37 therefore introduces a new commit protocol. It is not a storage wrapper around the
current mutable object.

## Identifier ownership

Opaque IDs are generated by the injected `IdSource`; database sequences are never used as public
identifiers.

| Identifier | Prefix/source | Owner | Notes |
|---|---|---|---|
| `workspace_id` | existing `ws` | Workspace service | Existing authority; never regenerated by Stage 4 |
| `session_id` | existing `ses` | Session application service | One durable interaction container |
| `task_run_id` | `task` | Task application service | One foreground user goal |
| `turn_id` | existing `turn` | turn-submit service | One accepted User input |
| `agent_run_id` | `arun` | AgentRun service | One model/tool-loop attempt; no longer aliases Turn |
| `conversation_record_id` | `rec` | ConversationLog durable boundary | Immutable record identity |
| `command_id` | `cmd` | calling client/application adapter | Retry-sensitive command receipt identity |
| `client_message_id` | caller-provided opaque value | turn-submit command | Idempotency field; not a chat-message field |
| `tool_execution_id` | `tex` | execution journal | One call attempt |
| `approval_id` | `apr` | approval service | Opaque, one-shot approval identity |
| `artifact_id` | `art` | Artifact service | Managed-file identity |
| `checkpoint_id` | `chk` | context service | Immutable projection identity |
| `grant_id` | `grt` | grant service | User-command-created authority |

IDs are validated as bounded opaque strings. Their prefixes aid diagnosis but never grant access or
replace workspace/task/run foreign-key checks.

## Three independent order domains

The word `sequence` must not represent three different clocks:

| Name | Scope | Authority | Purpose |
|---|---|---|---|
| `conversation_position` | one Session | conversation journal transaction | Immutable User/Assistant/Tool/terminal order |
| `runtime_event_sequence` | one Turn attempt stream | current AgentLoop | Ephemeral public event ordering |
| `application_event_cursor` | Operational Store | application-event table | Durable audit/query cursor introduced in Subplan 43 |

They are never compared, copied, or used to reconstruct one another. The current
`MessageRecord.sequence` migrates semantically to `conversation_position`; the current
`AgentEvent.sequence` migrates semantically to `runtime_event_sequence` without changing its wire
field before the public-event hold point.

## Store, Session, and Task states

Store health, Session lifecycle, and Session health are orthogonal:

```text
store_health:    ok | read_only | needs_repair | future_schema
session_lifecycle: active | archived | deleted
session_health:  ok | needs_recovery | quarantined | read_only
```

- `deleted` is a tombstone; physical deletion/export belongs to Stage 10.
- `needs_recovery` applies only to interrupted Session work.
- quarantine changes `session_health`, never lifecycle.
- a store-level failure may force Session reads into a derived read-only view, but does not rewrite
  every Session row.

### TaskRun state machine

Subplan 37 persists only a current TaskRun pointer and an `open` TaskRun row. Subplan 40 owns and
implements this complete state machine:

```text
[*] → open
open → ready_for_acceptance       final Assistant closes a successful Turn
ready_for_acceptance → open       ordinary follow-up; record continuation/correction evidence
ready_for_acceptance → accepted   explicit /accept
open → cancelled | failed | abandoned
ready_for_acceptance → cancelled | abandoned
failed → open                     explicit retry/resume as a linked attempt
accepted | cancelled | abandoned → [*]
```

`ready_for_acceptance` is non-terminal. It means the latest answer has been presented, not that
Morrow has proven the user's goal complete and not that Stage 5 may learn from it. `accepted` is
explicit. `waiting_approval` and `needs_recovery` are execution/Session states, never TaskRun states.

Subplan 40 does not persist a new TaskOutcome for every final assistant answer. It creates an
immutable Outcome version only for explicit acceptance, explicit outcome snapshot, or a terminal
cancel/fail/abandon transition. Follow-ups before that are durable continuation/correction evidence
and feed the next projection.

## Turn and AgentRun

- One accepted turn-submit command creates exactly one Turn and one UserMessage.
- A Turn may contain multiple AgentRuns after crashes or explicitly recoverable model interruption.
- The first attempt has no `resume_of_agent_run_id`; a resumed attempt points to the interrupted
  AgentRun.
- Resume with no new user input creates a new AgentRun in the same open Turn and never appends a
  second UserMessage.
- New user input creates a new Turn only after blocking recovery work is resolved or the prior Turn
  is truthfully closed.
- A recovered AgentRun resolves a new permission context. It does not inherit a prior run-bound
  CapabilityGrant.

Subplan 37 stores a bounded non-secret base run snapshot: resolved Profile/Preferences/config values
and source revisions/hashes, Provider/Model, RunPolicy/Tool schema digests, base Stage 3 permission
profile, and runtime instance identity. The full `PermissionSnapshot` and grant link are added only
by Subplan 44.

## Turn-submit idempotency

`client_message_id` belongs to the turn-submit command envelope and its receipt. It is not added to
`UserMessage` and is not sent to the Provider.

Uniqueness is `(session_id, client_message_id)`. A receipt stores the canonical request digest,
accepted Turn ID, current disposition, and final command result when available.

| Durable state | Same key + same request | Same key + different request |
|---|---|---|
| no receipt/User commit | handle as first submission | handle as first submission |
| accepted; Turn open or AgentRun interrupted | return existing receipt and recovery disposition; an explicit resume may create a new AgentRun in the same Turn | conflict |
| accepted; Turn closed | return the committed result; append no User and start no AgentRun | conflict |

The exactly-once invariant is **one Turn acceptance and one UserMessage per client message ID**.
It is not “only one model invocation forever.” Duplicate turn-submit itself never bypasses recovery;
the recovery command owns any additional AgentRun.

Command receipts are required only for turn submit, approval/recovery resolve, grant create/revoke,
and retry-sensitive Session/Task mutations. Queries do not create receipts.

## Durable ConversationLog append protocol

ConversationLog remains the grammar authority. The new durable append boundary uses this only legal
order:

```text
construct candidate records without mutating the live projection
→ validate candidate against the current immutable snapshot
→ BEGIN IMMEDIATE
→ write conversation rows and the command/run companion rows owned by this operation
→ COMMIT
→ replace/update the in-memory projection from committed rows
```

If validation, begin, write, or commit fails, the live projection stays unchanged. There is no
“mutate `_records`, then flush later” path. SQLite allocates the committed
`conversation_position`; restored snapshots must pass the same ConversationLog grammar.

AgentLoop remains the ordinary-chat caller. Task/Session services may coordinate a transaction but
cannot manufacture User, Assistant, Tool, or terminal records. SQLite adapters never import into or
write around ConversationLog from ContextBuilder.

### Recovery append

Recovery has one narrow exception to ordinary AgentLoop ownership. For an already-persisted open
ToolCycle it may atomically append:

1. one ordered ToolMessage per unresolved call, marked with an interrupted/error envelope; and
2. the corresponding non-success Turn terminal record when the recovery decision closes the Turn.

Recovery cannot append UserMessage, AssistantMessage, or a successful ToolMessage. It cannot edit
or delete old records. Only after this closure passes ConversationLog validation may ContextBuilder
build another request.

`reset`, `restore`, and `fork` remain explicit ConversationLog/application operations. SQL helpers
cannot clear or splice history.

## Public runtime event ordering

Subplan 37 changes the internal ordering from:

```text
emit turn.started → begin_turn
```

to:

```text
commit Turn + UserMessage → emit turn.started → invoke Provider
```

The public event type, payload, cardinality, and per-Turn ordering remain unchanged. The event now
truthfully means “the Turn was accepted durably.” `application_events`, introduced later, are a
separate durable audit stream and never reconstruct ConversationLog or token deltas.

## `/new`, `/exit`, and process-local `dirty`

Once Subplan 37 activates durable conversation:

- `/new` creates and selects a new Session; it does not call `ConversationLog.reset()` on the old
  Session and does not delete or archive it automatically;
- the old Session remains resumable with its existing lifecycle;
- Session-scoped Preferences do not carry into the new Session; global/workspace resolution still
  applies;
- if the current Session needs recovery, `/new` is blocked until the user resolves or truthfully
  closes that work;
- `/exit` flushes/ends the current foreground operation and closes the store; it never asks to
  “discard saved conversation”;
- if shutdown cannot prove an effect complete, it records `needs_recovery` and tells the user the
  work will remain for recovery rather than deleting it;
- the current `dirty` flag and its discard copy are removed or redefined as transient UI/run state,
  never “conversation is not saved.”

Subplan 37 updates the system boundary, README/architecture now-statements, terminal behavior, and
the Stage 3 tests that currently require chat to write no state document. Those tests become
positive durability/isolation assertions rather than being deleted without replacement.

## Context limit during rollout

Subplan 37 guarantees only bounded scripted no-tool Sessions. Existing ContextBuilder admission and
failure remain truthful for long histories until Subplan 42 adds durable checkpoints. No Subplan 37
gate may claim arbitrary-length Session continuation.

## Rejected alternatives

- storing `client_message_id` in UserMessage;
- one AgentRun per Turn under all crash conditions;
- treating every final Assistant as an accepted/terminal TaskRun;
- a second SQL-only message grammar or asynchronous conversation flush;
- using public runtime event sequence as durable conversation order;
- deleting persisted history on `/new` or `/exit`;
- inheriting a previous AgentRun's Full Access grant during recovery.
