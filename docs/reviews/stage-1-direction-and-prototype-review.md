# 阶段 1 路线 Review

> 对象：[阶段 1：方向确定与可运行原型](../roadmap/stage-1-direction-and-prototype.md)  
> 对照：[开发路线总览](../ROADMAP.md)，以及阶段 2–7 草案  
> 日期：2026-08-13  
> 结论：**产品方向正确，阶段切分大体正确，阶段 1 作为“可运行原型”过重。** 现在最该锁的是身份、所有权、隔离和写入契约；最不该锁死的是会话状态机、自然语言配置全链路和 25 项验收门禁。

---

## 0. 一句话判断

阶段 1 想验证的事情是对的：在真实项目目录里连续对话，并留下可恢复的下一棒。文档把这件事讲清楚了，也避开了 LangChain、SQLite、记忆检索、工具循环这些常见的过早承诺。

但当前文本已经不是“1–2 个有效开发日的原型说明”，而是一份接近产品内核的规格书。它提前实现并锁死了本该属于阶段 4（会话生命周期）、阶段 5（Provider 管理面）和阶段 7（打磨与不可逆删除）的行为。如果按“路线层面暂无待确认事项”去实施，后面改会话、记忆和工具触发路径的成本会明显高于现在把范围切薄。

**建议：保留方向和数据模型，把阶段 1 拆成“先证明闭环，再补齐产品面”。不要把整份 800 行规格当作第一刀实现合同。**

## 1. 总评

| 维度 | 判断 | 说明 |
|---|---|---|
| 路线总方向 | 正确 | 先编程助手、后通用助理；连续性优先于工具数量 |
| 阶段顺序 | 正确 | 对话与状态 → Agent 循环 → 本地工具 → 会话记忆 → 扩展 → 自动化 → 产品化 |
| 阶段 1 目标陈述 | 正确 | 验证方向，而不是做出能改代码的 Agent |
| 阶段 1 实际工作量 | 不合理 | 与“原型 / 1–2 日”严重不符 |
| 能否实现 | 能 | 没有研究难题，全是工程 |
| 架构骨架 | 合理偏重 | 分层方向对，缺编排层和上下文组装层 |
| 过早设计 | 明显 | 会话矩阵、NL 配置、完整 Provider CLI、`/undo`、25 项锁死验收 |

文档质量本身很高：概念分得清，禁止项明确，失败语义认真，测试分层专业。问题不在写得不够细，而在**把“以后几乎肯定要做的产品内核”误写成了“原型必须一次做完且不可改”。**

## 2. 路线设计是否正确

### 2.1 总览层是对的

总览里的差异化成立，而且比“再做一个带工具的 CLI Agent”更值得做：

- 以个人、而不是多用户平台为中心
- 以工作空间隔离上下文
- 用户拥有并可导出迁移数据
- 本地状态优先
- 核心与扩展解耦
- 分阶段演进

阶段顺序也符合这个定位。连续性是 Morrow 的产品主张，所以先做“对话 + 项目档案 + 交接”，再做工具循环，再做真实文件/终端，是对的。如果反过来先做工具，阶段 1 验证的就只是“又能调模型了”，无法回答 Morrow 为什么存在。

阶段 4 自己也写了：阶段 1 的交接只应是**轻量连续性验证**，完整会话与长期记忆留到后面。这个分工在总览层是清楚的。

### 2.2 阶段 1 文档和总览已经不一致

| 总览 / 阶段标题说的 | 阶段 1 正文实际要求的 |
|---|---|
| 方向确定与可运行原型 | 接近完整的个人 Agent 内核规格 |
| 终端连续对话，并保持项目交接 | 再加三层配置、NL 补丁、Provider 生命周期、会话状态机、单步撤销、工作空间遗忘 |
| 1–2 个有效开发日 | 按正文验收，更接近 10–20 个专注开发日 |
| 阶段 4 才做完整会话 | 阶段 1 已有 attached/detached、revision、12 格矩阵、`--discard`、双超时 |
| 阶段 5 才扩展模型管理 | 阶段 1 已有通用 add/list/show/configure/test/remove |
| 后续阶段进入时再确认 | 阶段 1 宣布“暂无待确认事项”，并锁死 25 条断言 |

不是方向错了，是**阶段 1 把后面几个阶段的产品面提前吃进来了**。

### 2.3 和 Hermes 的关系处理得大体正确

“受 Hermes 启发，不复制 Profile”是对的。该学的学到了：

- 状态放在用户主目录，不写进项目仓库
- 档案与当前进度分开
- 密钥不进普通配置
- 先做可替换边界，不把核心写成框架绑死

不该这么早学的，也已经学进来了：

- 命令面很宽，还没开始用就按完整产品设计
- 会话/交接状态机过细
- 配置系统本身先变成了一个产品

Hermes 是多年产品叠出来的厚度。阶段 1 要验证的是“下一棒”这件事有没有人需要，不是复刻一套同等厚度的管理面。

## 3. 阶段 1 工作是否合理

### 3.1 应该留在阶段 1 的工作

这些工作直接服务两个验证目标，应该做：

1. 能在项目目录启动并认出工作空间
2. 首次认证，密钥进钥匙串，不进 YAML
3. 同一进程内连续对话，流式输出，第一次 `Ctrl+C` 只取消本轮
4. 工作空间级 `profile.yaml` + `handoff.yaml`，彼此隔离
5. 启动时展示上次交接，由用户决定是否带进本次上下文
6. 结束时尽量留下下一棒；失败则保留旧交接
7. 查看档案和交接的只读入口
8. Fake Provider、离线测试、密钥不落盘

这已经足够回答：方向对不对，以及“模型调用 + 工作空间隔离 + 基础状态保存”能不能稳定工作。

### 3.2 可以锁数据模型、但不必做完整产品面的工作

这些概念应该现在定，实现可以很薄：

- Adapter / Provider 实例 / Model / `ModelRef`
- 三层偏好的覆盖与列表合并语义
- Profile / Handoff / Preferences 三分
- YAML 布局、`schema_version`、`revision`、原子写、一份 `.bak`
- `AgentEvent` 信封和阶段 1 的五种事件
- `ModelProvider.stream()` / `complete()`

“结构按集合预留，运行时只验收一个 Provider、一个模型”这件事是对的。错在把完整 CLI 和完整验收一起提前做完。

### 3.3 不应该算进阶段 1 完成定义的工作

| 工作 | 为什么过早 | 更合适的位置 |
|---|---|---|
| 12 格会话矩阵 + S/D/C + `--discard` + 60s/20s + 单次 Schema 修复 | 这是会话产品，不是原型验证 | 阶段 4，或阶段 1 之后的 1.5 |
| 每轮自然语言结构化抽取三分支 | 双模型调用，误写风险高，阶段 2 几乎一定会被工具路径替代 | 先用斜杠命令和少量启发式；抽取作为试验 |
| 完整 Provider CLI（尤其 `configure` / 事务性回滚 / 分步删凭据） | 阶段 1 只有一个预设 | 首次向导 + `list/show/test`；其余阶段 5 |
| `/undo` 恢复绑定模式 + 检查点 + 元数据三元组 | `.bak` 已能满足崩溃恢复 | 主闭环能用之后再加 |
| `workspace forget` 作为不可撤销产品能力 | 验证隔离不需要遗忘命令 | 阶段 4/7 的数据管理 |
| `/config edit` 交互向导 | 查看和一层写入就够 | 使用后按痛点补 |
| 25 个锁死自动化 ID + PTY harness + AST 禁区扫描作为阶段门禁 | 测试平台本身就超过“1–2 日” | 行为清单保留，门禁先收成 P0 |

### 3.4 时间估计必须改

“1–2 个有效开发日”和正文工作量不兼容。粗估：

| 切片 | 更真实的工作量 |
|---|---|
| P0：启动、认证、流式对话、workspace、最小 handoff | 3–5 日 |
| P1：三层配置查看/写入、原子写、简单 `/new` `/continue`、Provider 只读与 test | 再 3–5 日 |
| P2：NL 抽取、完整会话矩阵、`/undo`、forget、TerminalHarness 全矩阵 | 再 5–10 日，且 PTY 测试容易拖长 |

按当前正文一次验收，按单人认真做，更接近 **2–4 周**，不是 1–2 日。如果坚持 1–2 日，只能验收 P0，不能验收 25 条。

## 4. 能否实现

**能实现。** 没有算法难题，也没有依赖未发明的基础设施。风险全是工程和产品风险。

### 4.1 技术栈可行

Python 3.12、`uv`、asyncio、OpenAI 兼容 SDK、Typer、prompt-toolkit、Rich、Pydantic v2、PyYAML、keyring、pytest、Ruff，都匹配这个阶段。不引入 LangChain / FastAPI / SQLite / Textual / MCP，也正确。

真正难的不是 YAML 存储，而是：

1. **prompt-toolkit + asyncio + Rich 流式渲染 + `Ctrl+C` / `Ctrl+D`。** 这是阶段 1 最大的实现风险，文档着墨最少。
2. **用 Flash 模型做严格 JSON Schema。** 交接生成和配置抽取都依赖它。
3. **伪终端集成测试。** prompt-toolkit / Rich 的 PTY 测试天然容易抖。

这些都能做，但不属于“两天原型”的确定性工作。

### 4.2 首个模型服务可行，但不能把模型质量写进完成定义

OpenCode Go + `deepseek-v4-flash` + OpenAI-compatible Chat Completions 作为第一预设是合理的：有公开端点、模型 ID 匹配、适配器类型正确。

需要提前当成已知风险，而不是默认“模型一定听话”：

- OpenCode Go 的模型目录会变，已经出现过 Flash 正式版 / 预览版 / 实际返回模型不一致的讨论
- Flash 带 reasoning。如果 Adapter 只读 `delta.content`，界面会长时间空白，或把思考过程喷进正文
- 结构化输出即使标注支持，也不等于 `ConfigPatch` 和完整 Handoff Schema 会稳定一次通过

阶段 1 应锁 Adapter 协议和预设数据，不锁“这个模型永远叫这个名字、永远能填满 Schema”。

### 4.3 有几处“能写进文档，但运行时会经常失败”

- `/exit` 的自动交接只有 20 秒，失败则丢这轮连续性。产品承诺是“留下可靠的下一棒”，实现却把可靠性完全交给一次短超时的模型调用。
- 若每条用户消息都先 `complete()` 再 `stream()`，正常对话延迟和费用直接翻倍，澄清分支还会打断聊天。
- `S1-A10` 要求子进程 API 从未调用，但工作空间识别若走 `git rev-parse` 就会失败。必须改成进程内向上查找 `.git`，或把 git 探测从禁区里豁免。

## 5. 架构是否合理

### 5.1 应该保留的骨架

依赖方向是对的，后续也应该守住：

```text
interfaces  →  runtime / services  →  core
adapters 实现 core 的 Protocol
bootstrap 是唯一组装点
```

尤其该保留：

- `core` 不依赖 OpenAI SDK、Typer、Rich、PyYAML、keyring
- Provider 预设只是数据，不是业务分支
- 按 `adapter_id` 注册，禁止 Provider 名称 `if/elif`
- YAML 是适配器，不是业务协议
- 模型不直接读写 YAML
- 界面不直接碰密钥和状态文件
- 不为工具、记忆、Skills、调度器预建空模块

`AgentEvent` 作为回合输出边界、`ModelEvent` 作为 Provider 内部归一化，这两层也该留。阶段 7 若加 TUI / Web，这个形状能复用。

五个 Protocol 的数量合适，不必再加一堆空接口。

### 5.2 缺了两个会立刻长出来的组件

文件树里有 `agent.py`、`session.py`、四个 service、两个 interface，但阶段 1 真正的主循环并不只是 `run_turn`。一次用户输入至少可能是：

- 斜杠命令
- 会话控制（`/new` `/continue` `/exit`）
- 自然语言配置抽取
- 普通流式对话
- 退出时的交接生成

如果这些都塞进 `AgentRuntime`，它会变成上帝对象，阶段 2 的工具循环会更难放。如果塞进 `interfaces/terminal.py`，又会破坏“界面只消费事件、不碰状态”。

文档还要求“会话启动时冻结配置和 Profile 快照”，但没有任何名为上下文组装的模块。而 Morrow 的产品主张——它知道这是哪个项目、上次做到哪里——恰恰发生在这里。

建议把架构补成：

```text
interfaces/terminal
    → SessionOrchestrator / ReplApp      # 输入分发、确认、退出码
        → CommandService                 # /config /workspace /handoff /new ...
        → ConfigExtraction (可选)        # 只在通过门控后调用 complete()
        → ContextBuilder                 # 拼 system + profile + 可选 handoff + 消息
        → AgentRuntime.run_turn()        # 一轮模型流式输出
        → HandoffService                 # 显式更新或退出时保存
```

`run_turn` 应继续表示**一轮模型调用**，不要许诺阶段 2 仍不改入口。阶段 2 应新增 `run_task()` 或等价循环，内部多次调用模型/工具。阶段 1 正文里“阶段 2 无需改变现有运行入口”过早，也容易把工具循环硬塞进单轮 API。

### 5.3 `ProjectStateStore` 偏宽

一个 Protocol 同时读写全局配置、Profile、Handoff，阶段 1 能用。阶段 4 一旦出现会话库和记忆库，这个接口会被迫膨胀，或被拆开并连带改所有调用方。

现在不必拆实现，但应在路线里写明：它是门面，项目级操作继续强制带 `workspace_id`；会话存储以后是另一个端口，而不是往这个接口上继续加方法。

### 5.4 事件协议：锁形状，别锁未来名字

现在锁这些是值得的：

- 统一信封
- `turn.started` → 中间事件 → 唯一 `turn.completed`
- `sequence` 是顺序权威，`timestamp` 只是观测时间
- 取消是 `finish_reason: cancelled`，不是伪错误
- 消费者忽略未知类型和未知字段
- 公开事件不含密钥和原始 SDK 对象

这些不值得现在锁：

- 阶段 2 的 `tool.requested` / `approval.required` 等具体名字  
  阶段 2 自己还写着“进入阶段时再确认”
- 每个 `text.delta` 都必须带齐可观测字段的存储/持久化语义  
  阶段 1 事件只在进程内消费，做成完整事件总线过重

### 5.5 文件树不必当合同

文档已经说不承诺文件树永久不变，这是对的。实施时按上面的编排层和 `ContextBuilder` 增删文件即可，不要为了“看起来像六个月后的产品”先把目录铺满。

## 6. 哪些边界应该提前固定

这些改起来都贵，现在就应写成不变式。其中一部分文档已经写对了。

### 6.1 已经锁对、应保持

1. **状态在 `~/.morrow`，不写项目仓库。**
2. **密钥只进 `CredentialStore`（钥匙串 / 环境变量），不进 YAML、日志、终端回显。**
3. **工作空间按项目隔离；Git 分支不参与身份。**
4. **Profile = 相对稳定事实，Handoff = 当前接力，Preferences = 协作方式。三者分文件、分命令。**
5. **模型只输出受限补丁，程序校验后再原子写。**
6. **Adapter / Provider 实例 / Model 三分；运行时只收已校验 `ModelRef`。**
7. **自然语言不能改连接设置、凭据、`workspace_id`、权限。**
8. **阶段 1 不读源码、不改项目文件、不跑命令、不存完整聊天。**
9. **标量覆盖、列表按作用域合并、`unset` 露出下一层，不写空串占位。**
10. **启动发现 Handoff 只展示，不静默注入。**
11. **失败不覆盖最后一份有效状态。**

### 6.2 现在还没锁死、但必须补锁

这些比会话矩阵更值得先写清楚。

#### A. 工作空间身份算法

现在只有优先级，没有算法。后面所有隔离测试都建立在它上面。

应固定：

- 规范化：`expanduser` → 绝对路径 → 解析符号链接 → 去掉尾斜杠。在 macOS 上明确是否做大小写折叠。
- Git 根探测：进程内向上查找 `.git` 目录或 gitfile，不调用子进程。找不到则用当前目录。
- `workspace_id`：随机生成一次，之后稳定；路径只是索引，不是身份。
- 仓库被移动：索引找不到规范化路径时，不得默默新建并丢掉旧档案。至少要提示“这像是已登记工作空间的新路径”，让用户认领或新建。
- `git init` 之后：原先按目录登记的工作空间，是继续用旧 ID，还是改绑到新的 Git 根，必须有一条规则。建议：已有索引命中则保持 ID，只更新根路径。
- Git worktree：不同工作目录视为不同工作空间。
- 显式指定目录的 CLI 形状：`morrow --dir <path>` 或等价物，现在正文没有命令形态。

身份比 `/new` 的 12 个单元格更基础。

#### B. 路径索引与并发

- `revision` 字段已经有了，应明确用于乐观并发：磁盘 revision 与预期不符则拒绝覆盖，而不是静默 last-write-wins。
- 阶段 1 可以声明：同一工作空间不支持多进程同时写入；跨进程最多用 lock 文件或 revision 冲突报错。
- `workspace forget` 只检查当前进程是不够的，至少应检查 lock / 活跃标记。

#### C. 上下文组装契约

这是产品核心，正文几乎没写。应固定阶段 1 的最小 context pack：

```text
system:
  - 身份与能力（不能读文件、不能跑命令、不能假装已执行）
  - 合并后的 preferences
  - profile（若有）
  - handoff 快照（仅 attached）
messages:
  - 本进程内的用户/助手消息，按原序
```

还应固定：

- 会话中的偏好 / Profile / Handoff 修改**立即进入下一轮上下文**。  
  “启动时冻结快照”只能表示启动基线，不能表示本轮对话里改了也不生效。
- 阶段 1 的截断策略可以很笨：超长则保留 system + 最近 N 轮。不规定的话，真实项目里一次长粘贴就会把程序打崩。
- System Prompt 需要大纲，不需要文学稿。

#### D. 一轮输入的处理顺序

这是当前规格最大的实现空洞。必须先定，否则 `run_turn`、抽取和斜杠命令会互相踩。

建议锁成：

```text
输入
 → 斜杠命令：本地处理，默认不走模型
 → 否则（可选）门控：像“记住 / 以后 / 这个项目 / 这次”才抽取
 → 若 config_patch / clarification：走配置路径，本轮不再流式闲聊
 → 否则：组装上下文，stream() 对话
```

不要默认“每条消息先 `complete()` 再 `stream()`”。那会把阶段 1 的主路径变成双调用，也会让阶段 2 变成“抽取 + 工具循环”三截。

#### E. 交接失败时的确定性兜底

产品承诺是可靠下一棒，所以不能只有“模型失败就保留旧文件并 `exit 2`”。应增加：

- 优先：模型生成完整 Schema
- 失败：用当前 `current_goal`、最近用户消息和已有字段写一份最小合法 Handoff
- 只有磁盘/校验本身失败，才保留旧文件并返回 2

否则阶段 1 最重要的闭环会经常在退出时断掉。

#### F. 推理内容与可见文本

Adapter 必须把 Provider 特有的 reasoning 字段收掉，只把用户可见答案变成 `model.text.delta`。阶段 1 可以显示“正在生成”，不要把思考过程写进 Handoff 或消息历史。

#### G. 错误码与重试

事件里有 `code`、`retryable`，正文没有枚举。阶段 1 锁一小个就够：`auth`、`network`、`rate_limit`、`timeout`、`invalid_response`、`cancelled`、`internal`。聊天重试次数、是否重试流式中断，也应各有一句，避免 `status.changed` 写了“重试”却没有策略。

#### H. 首次进入工作空间的字段

“项目要达成什么”不要写成 `profile.summary` **或** `profile.goals[]`。应固定：

- 项目要达成什么 → `profile.summary`
- 现在推进哪一步 → `handoff.current_goal`
- 用户跳过 → 两者皆空，`detached`

## 7. 哪些设计属于过早设计

### 7.1 会话 / Handoff 状态机

`attached` / `detached`、revision 快照、检查点、五种 `/status`、12 格矩阵、`--discard`、双超时、单次 Schema 修复，合在一起已经是完整会话产品。

它和阶段 4 的关系尤其危险：

- 阶段 1 把绑定关系只放在进程内存
- 阶段 4 要持久化会话、恢复会话、压缩上下文
- 若现在把 12 格矩阵写成不可改验收，阶段 4 要么推翻重做，要么在一个为“不落盘”设计的模型上硬补持久化

阶段 1 真正需要的只是：

```text
启动看到交接 → 用户选择带或不带 → 结束时按选择决定写不写
```

用两个布尔值就能表达：`handoff_loaded`、`dirty`。不必先发明五种对外状态名。

`/new`、`/continue` 可以作为薄命令留下，但不要把取消、丢弃、保存失败、超时修复全部锁成阶段 1 门禁。

### 7.2 自然语言配置全链路

ConfigPatch、字段白名单、作用域组合、双入口共用 `ConfigService`，作为**写入契约**是优秀设计，应该保留 Schema。

过早的是把它做成阶段 1 主路径：

- 普通对话 / 歧义 / 敏感字段都要有自动化断言
- 这意味着实现上很难避免每轮都抽取
- Flash 模型会误判“这个项目……”类闲聊
- 阶段 2 一旦有工具，配置更自然的入口是工具，而不是平行的抽取循环

阶段 1 用 `/config`、`/workspace edit`、`/handoff edit` 就能验证三层模型和白名单。自然语言抽取可以做试验，不要做完成门禁。

### 7.3 完整 Provider 管理面

动态 ID、集合结构、`active_model`、删除后不静默切换，这些该锁。

`provider configure` 的 Adapter Schema 向导、添加失败回滚新凭据、删除时二次询问是否删钥匙串，是产品完成度，不是原型必要条件。首次向导 + `test` + `list/show` 就能验收“不用手改配置文件”。

阶段 5 已经规划 `model use/add/remove`。阶段 1 再把管理面做满，两边会抢同一组命令的语义。

### 7.4 `/undo`

单步撤销体验好，但和 Handoff 绑定模式、检查点、`.bak` 缠在一起后，正确性很脆。阶段 1 有原子写和一份 `.bak` 已经能处理崩溃。`/undo` 应从完成标准里拿掉。

### 7.5 测试平台本身

`ScriptedModelProvider`、`MemoryCredentialStore`、`AppFactory`、`NetworkGuard` 很值，而且相对稳。

`TerminalHarness` 驱动真实 prompt-toolkit 去覆盖 12 格矩阵、S/D/C、`Ctrl+C`/`Ctrl+D`、信号，是另一个项目。阶段 1 更好的集成方式是：绕过 TTY，直接往 Orchestrator 注入命令。界面层单独测取消和渲染。

架构 AST 扫描可以留一个很窄的版本：`core` 不得导入 SDK / Typer / Rich。不要在第一周就靠扫 AST 证明“没有文件工具”。

### 7.6 “不为未来预建空模块”和正文自我矛盾

文档一边禁止空模块，一边已经：

- 预留阶段 2 事件名
- 按多 Provider 产品面实现 CLI
- 把 `run_turn` 许诺为未来也不改的唯一入口

前向设计应停在数据模型和依赖方向，不要停在未经验证的命令矩阵和事件点名。

## 8. 过重设计会怎样影响后续

| 现在锁死的东西 | 后续冲击 |
|---|---|
| 每轮结构化抽取 | 阶段 2 变成抽取 + 工具循环；配置出现两条触发路径。若以后用工具写配置，阶段 1 的抽取要么删，要么双轨长期并存 |
| `run_turn` 永不改入口 | 工具循环会被塞进单轮 API，或界面层自己写第二套循环 |
| 进程内 attached/detached/revision | 阶段 4 持久化会话时必须迁移这套语义，或放弃阶段 1 用户已经习惯的行为 |
| 单一 `ProjectStateStore` 读写一切 | 阶段 4 引入 SQLite/会话库时，调用面一起改 |
| 25 条断言不可削弱 | 任何简化都要先改路线，原型迭代会变慢 |
| 交接只相信模型 Schema | 用户会觉得“连续性”不可靠，阶段 4 再补记忆也修不回信任 |
| 过宽的斜杠命令面 | 阶段 3/4/5 的命令只能往已经拥挤的命名空间里塞，取消成本变高 |

相反，下面这些“看起来像提前设计”的东西其实不重，后续也用得上：

- `ModelRef` 和动态 Provider 映射
- 事件信封 + 忽略未知字段
- ConfigPatch 白名单
- 原子写 + `schema_version`
- Fake Adapter 可注册第二个 Provider

区分标准是：**锁契约，不锁完整产品行为。**

## 9. 文档内部的矛盾和空洞

### 9.1 直接矛盾

1. **时间 vs 范围。** 1–2 日 vs 25 项锁死验收 + 完整管理面。
2. **冻结快照 vs 立即落盘。** 若下一轮上下文仍用启动快照，用户刚说“以后用中文”不会生效。这应视为规格错误，而不是实现细节。
3. **不调用子进程 vs 用 Git 认仓库。** `S1-A10` 必须改。
4. **轻量交接 vs 完整会话操作系统。** 和阶段 4 的分工冲突。
5. **不预建未来模块 vs 预锁阶段 2 事件和完整 Provider CLI。**
6. **总览“讨论中” vs 阶段 1“暂无待确认事项”。** 下面第 11 节全是未决问题。
7. **首次回答写入 `summary` 或 `goals[]`。** 验收无法稳定断言。

### 9.2 关键空洞

1. 普通消息、抽取、斜杠命令的主循环顺序
2. System Prompt / ContextBuilder 的内容与更新时机
3. 工作空间路径规范化、搬家、`git init`、worktree
4. `morrow` 的调用形态：默认进 REPL？`--dir` 怎么写？
5. reasoning 字段怎么处理
6. 聊天是否重试、重试几次
7. 抽取失败、澄清、普通回复是否互斥
8. 列表项是对象时，`remove` 的精确匹配规则（`decisions[]`）
9. `instructions[]` 高优先级放后面的原因（对模型注意力是对的，应写明，避免以后被“改回前面”）
10. 多进程同时打开同一工作空间
11. `~/.morrow` 无法创建或权限失败时的行为
12. 未知 `schema_version` 是拒绝启动还是只读降级

### 9.3 较小但应顺手修的点

- 阶段 1 有 `model current`，没有 `model use`。若 `configure` 能登记第二个模型，当前模型怎么切，应写一句：阶段 1 只允许向导结束时设置 `active_model`，切换留给阶段 5。
- `decisions[]` 做成对象、其余列表都是字符串，阶段 1 没有必要。全部用字符串更简单；需要原因时写成一句话。
- 界面文案全是中文，同时又有 `language` 偏好。阶段 1 应宣布：产品 UI 先中文，`language` 只约束模型回复，不做完整 i18n。
- Live 测试依赖真实 OpenCode Go，预设的 `base_url` 现在还是占位符，实现前必须写成真实常量并与官方文档核对。

## 10. 验收与测试怎么改才合理

测试分层思想是这份文档最好的部分之一，应保留，但不要整包作为原型门禁。

### 10.1 建议的 P0 门禁

对应“原型真的能证明方向”：

1. 空状态首次启动，向导写入预设 Provider，密钥不出现在 YAML / 日志 / 终端
2. 同一进程连续多轮对话，后续请求带上完整消息序
3. 流式分片顺序正确；`Ctrl+C` 取消本轮后还能再聊
4. 两个工作空间的 Profile / Handoff 互不出现
5. 启动展示交接但不注入；显式继续后才注入
6. 退出时尽量写新交接；模型失败则确定性兜底或保留旧文件，绝不写半份
7. Fake Adapter 可再注册一个 Provider，核心无名称分支
8. 哨兵证明阶段 1 不读项目源码、不写项目目录（Git 探测若用进程内找 `.git`，应对 `.git` 豁免）

### 10.2 建议降为 P1 / 阶段 1.5

- 自然语言三层写入与澄清
- `/config` 来源展示、`unset`、`instructions` 合并
- 12 格会话矩阵与 `--discard`
- `/undo`
- `workspace forget`
- Provider 添加失败的凭据回滚
- 完整 TerminalHarness 信号矩阵

### 10.3 测试实现建议

- 默认继续全离线、不碰用户 `~/.morrow`、不碰真钥匙串
- 集成测试打 Orchestrator，不打真 TTY
- 合同测试保住 `ModelProvider` / `CredentialStore` / 原子写
- Live 测试保持显式、不进默认 CI
- 可以保留 25 个测试 ID 当总清单，但正文应改成：“P0 通过即可进入阶段 2 讨论；P1 不阻塞工具循环设计”

否则会出现一种很差的节奏：阶段 2 已经能想工具循环了，人还在修 PTY 里 `/continue` 取消键的闪烁。

## 11. 建议改写后的阶段 1

### 11.1 重新定义完成

**阶段 1 完成 = 在任意项目目录启动 Morrow，能连续对话，能认出这是哪个项目，能在结束时留下下一棒，并且这些状态可隔离、可查看、失败可恢复。**

不是：个人 Agent 的配置操作系统 + 会话操作系统 + Provider 控制面一次性做完。

### 11.2 推荐切片

**P0 / 真正的阶段 1**

- `morrow [--dir PATH]` 进入 REPL
- OpenCode Go 首次向导 + keyring
- 流式对话、进程内历史、取消本轮
- workspace 识别与索引
- `profile.yaml` / `handoff.yaml`
- 启动提示交接；用户选择注入或不注入
- 退出写交接，失败有兜底
- `/workspace`、`/handoff` 只读
- `/exit`、`Ctrl+D`
- 离线 Fake Provider 测试

**P1 / 仍可算阶段 1，但不锁死细节**

- 三层 preferences 的查看与斜杠写入
- `/handoff update`、`/handoff edit` 的最小版
- `/new`、`/continue` 的简单语义
- `provider list/show/test`
- 原子写 + `.bak`

**P2 / 移出阶段 1 完成定义**

- 每轮 NL ConfigPatch
- 完整会话矩阵、`--discard`、双超时、Schema 修复
- `/undo`
- `workspace forget`
- 完整 Provider configure/remove 产品流
- PTY 级 25 项门禁

### 11.3 架构上现在就该写下、但实现保持薄

- `SessionOrchestrator` + `ContextBuilder`
- `run_turn` 只表示一轮
- ConfigPatch Schema 和字段白名单（即使第一刀只用斜杠命令往这个 Schema 里写）
- `ModelRef`、Provider 集合、事件信封
- 工作空间规范化算法和搬家规则

### 11.4 阶段 1 结束时不要写“暂无待确认事项”

至少留下这些问题，等 P0 跑过真实项目再定：

1. 自然语言配置是每轮抽取、启发式门控，还是等阶段 2 做成工具？
2. 交接是模型生成，还是模型 + 确定性模板双轨？
3. attached/detached 是否值得在持久化会话之前对外暴露？
4. `run_turn` 与阶段 2 循环的关系
5. 仓库搬家和 `git init` 的认领流程要做到多深
6. DeepSeek V4 Flash 的 reasoning 与结构化输出是否稳定到能当默认模型

## 13. 最终结论

阶段 1 路线在**产品判断**上是一份好文档：连续性、工作空间隔离、用户拥有数据、模型不直接碰状态、先对话后工具，这些都经得起后续几年演进。

它在**阶段设计**上过重：用原型的名字，写了内核产品的合同，并用“不可削弱的 25 项验收”把尚未被真实使用教训过的行为锁死。

它在**架构**上大体正确，但缺编排层和上下文组装层；最危险的不是六边形目录，而是每轮抽取和过早定稿的会话状态机。

它在**可实现性**上没有硬障碍，卡点是范围、终端异步交互、以及把 Flash 模型的结构化输出当成交接可靠性的唯一来源。

**如果只改三件事，改这三件：**

1. 把阶段 1 切回 P0 闭环：认出项目、连续对话、留下下一棒。  
2. 现在锁身份、所有权、隔离、写入契约、上下文组装；不要锁 12 格会话矩阵和每轮 NL 配置。  
3. 给交接一条不依赖模型成功的退路，否则差异化会在第一次失败退出时破产。

按这个改完，阶段 1 仍然能证明 Morrow 不是又一个聊天套壳；后面的阶段 2–4 也不用先拆除一套过早长成的内核。
